# ATTACK-MODEL.md — Модель угроз Mycerus DTN

**Версия:** 0.3.0
**Статус:** Заготовка для IMMUNE-SPEC-v0.1
**База:** Этапы 1–16 Mycerus MVP (MEB, MGR, POT, SNS/SRE, Vironet, trace-replay)
**Дата:** 2026-09-28

---

## 1. Область применения

Этот документ описывает модель угроз для сети Mycerus — DTN-маршрутизатора с эволюционирующей политикой протокола (Bundle Protocol 7 / RFC 9171). Модель охватывает атаки на Data plane (MEB, payload), Control plane (MGR, градиенты, POT), Evolution plane (Vironet, геномы, fitness) и Immune plane (сенсоры, кворум, контрмеры).

Цель документа — дать основу для проектирования Immune plane: шестислойной иммунной системы сети, в которой пенициллин-контрмеры служат исполнительным органом, а не самостоятельной защитой.

---

## 2. Модель противника

| Параметр | Предположение |
| --- | --- |
| **Возможности** | Контроль над ограниченным числом узлов (≤10% флота), перехват радиоканала, генерация bundle'ов, подделка challenge-response (без приватного ключа легитимного узла) |
| **Цели** | Снижение доставляемости, разделение сети (partition), исчерпание ресурсов, подрыв доверия к Vironet через ложные тревоги, смещение эволюции в свою сторону |
| **Ограничения** | Не владеет приватными ключами легитимных узлов (если захвачен — только свой); не может глушить весь спектр одновременно; действует в тех же условиях store-carry-forward |
| **Типы** | (A) Внешний — узлы без валидного genome_id; (B) Внутренний — скомпрометированный легитимный узел; (C) Сенсорный — узел-датчик, инициирующий ложные тревоги; (D) Коллюзионный — несколько легитимных узлов, сговорившихся |

**Ключевой инвариант Mycerus:** атака не может обрушить систему, пока не уничтожила почти всё. Это свойство архитектуры (Store-Carry-Forward, отсутствие центра, избыточность путей), а не активная защита.

## 3. Категоризация атак (6 категорий)

Все атаки разбиты на **6 категорий**. Для каждой угрозы указаны: целевой компонент, вектор атаки и концепция защиты (какой слой иммунитета срабатывает).

---

### Категория A. Атаки на идентичность и аутентификацию

*Атакующий пытается стать «своим» в сети или выдать себя за другое устройство.*

| ID | Угроза | Описание | Целевой компонент | Вектор атаки | Защита (слой иммунитета) |
| --- | --- | --- | --- | --- | --- |
| **A1** | **Sybil** | Один узел создаёт множество ложных идентичностей (genome_id), чтобы доминировать в маршрутизации или кворуме | SNS, MGR gradient table | Генерация ключевых пар Ed25519 без регистрации, массовая рассылка beacon'ов | **Слой 1:** SNS challenge-response с creator_signature; проверка genome_id в реестре Vironet. **Слой 2:** Детектор аномальной плотности новых узлов в окне контактов |
| **A2** | **Spoofed beacon** | Поддельный анонс (beacon) с чужим genome_id, пытающийся перенаправить трафик или внедрить ложный gradient | MGR, POT contact discovery | Перехват beacon'а легитимного узла, replay с модифицированным gradient/cost | **Слой 1:** Подпись beacon'а отправителем; freshness-nonce в контакте. **Слой 2:** Сверка заявленного genome_id с fingerprint открытого ключа, использованным в подписи |
| **A3** | **Impersonation** | Атакующий крадёт приватный ключ узла (или экстракт из захваченного устройства) и действует от его имени | SNS, MGR, Vironet voting | Node capture (физический) или side-channel экстракция ключа | **Слой 1:** Ротация ключей (TTL ключа в геноме). **Слой 5:** Ревокация скомпрометированного ключа через распространённый Threat-bundle; обнаружение двойного подписывания одного nonce двумя разными endpoint'ами |
| **A4** | **Replay auth** | Повтор старого challenge-response или старого SNS-handshake для прохождения аутентификации без знания приватного ключа | SNS/SRE | Перехват и повтор challenge-response из прошлого контакта | **Слой 1:** Nonce-кэш с окном времени + monotonic counter в SRE. **Слой 2:** Детектор повторов nonce из MGR-лога |
| **A5** | **Replay beacon** | Повтор старых beacon'ов захваченного или офлайн-узла для подделки его присутствия в сети | POT contact discovery, MGR | Перехват beacon'ов из прошлого, replay с поддельным timestamp | **Слой 1:** Freshness-nonce + epoch в beacon'е; старый beacon отклоняется. **Слой 2:** `BeaconFreshnessSensor`: отслеживает «возраст» beacon'а. Если beacon старше окна — флаг. **Слой 3:** Threat-bundle типа `stale_beacon` |

#### Концепция защиты Mycerus для категории A

**Обнаружение (Слой 2):**

- `SNSAnomalySensor`: мониторит частоту failed challenge-response по соседям. Базовая линия — медиана успешных аутентификаций за скользящее окно (N контактов). Отклонение >3×MAD → событие.
- `BeaconConsistencySensor`: при получении beacon сравнивает заявленный genome_id с fingerprint открытого ключа. Несоответствие → немедленный отказ в POT-contact.

**Контрмера (Слой 3 — пенициллин):**

- `PotMsg::Threat` с типом `identity_spoof` — подписанное утверждение: «узел с ключом K анонсировал ложный genome_id G в момент T».
- Действие: узлы, получившие Threat, добавляют (K, T, TTL) в локальный revocation-лист. При следующем SNS-handshake — отказ в доверии.
- **Важно:** пенициллин бьёт по *ключу*, а не по содержимому. Payload не трогается.

**Гиперчувствительность (Слой 4):**

- Активируется только при кворуме N=2 независимых сенсоров с положительной репутацией.
- Действие: исключение ключа из глобального gradient-table на срок `quarantine_ttl`.

### Категория B. Атаки на маршрутизацию и доставку

*Атакующий искажает маршрутную информацию или блокирует прохождение bundle'ов.*

| ID | Угроза | Описание | Целевой компонент | Вектор атаки | Защита (слой иммунитета) |
| --- | --- | --- | --- | --- | --- |
| **B1** | **Blackhole** | Узел принимает bundle'ы, но не передаёт их дальше (drop 100%) | MGR forwarding, POT relay | Нормальный SNS → принятие bundle → молчание | **Слой 2:** `DeliveryTrackingSensor`: сравнивает ожидаемую доставляемость (по gradient) с фактической. Узел, через который bundle'ы систематически исчезают, помечается. **Слой 3:** Понижение приоритета его gradient-обновлений, снижение copies для bundle'ов через него |
| **B2** | **Greyhole** | Избирательное дропание (например, только bundle'ы определённого destination или только при высокой нагрузке) | MGR forwarding | Условное drop на основе metadata | **Слой 2:** Статистический детектор: корреляция между прохождением bundle'ов конкретного dst через узел и их исчезновением. **Слой 3:** Деградация (degraded) — пауза relay для этого направления |
| **B3** | **Replay routing** | Повтор старых gradient-обновлений или старых bundle'ов для создания петель или переполнения таблиц | MGR gradient table, bundle store | Replay перехваченных `PotMsg::Gradient` или bundle'ов с поддельным timestamp | **Слой 1:** freshness-nonce и epoch во всех gradient-сообщениях. **Слой 2:** `GradientFreshnessSensor`: отклонение timestamp'а gradient от локального времени узла > threshold → отбрасывание. **Слой 3:** Threat-bundle типа `stale_gradient` |
| **B4** | **Eclipse** | Изоляция целевого узла или сегмента путём окружения ложными маршрутами и перехвата всех контактов | MGR, POT contacts | Sybil-узлы окружают жертву, перехватывают её контакты, подают ложные gradient'ы | **Слой 0:** Избыточность путей — eclipse работает только если атакующий контролирует все маршруты к жертве. **Слой 2:** `ContactDiversitySensor`: если узел видит резкое снижение числа уникальных соседей и одновременный рост одного «доминирующего» соседа — тревога. **Слой 4:** HR-изоляция сегмента только при кворуме |
| **B5** | **Sybil flooding** | Массовая регистрация ложных узлов для заполнения gradient-table и монополизации маршрутов | MGR gradient table, SNS | Генерация тысяч ключей, массовая рассылка beacon'ов, регистрация в Vironet | **Слой 1:** `new_node_rate_limit` — лимит на число новых узлов, принимаемых за контакт. **Слой 2:** `NodeDensitySensor`: аномальная плотность новых genome_id в окне. **Слой 3:** Rate limiting на приём gradient'ов от новых узлов; приоритет историческим соседям |
| **B6** | **Gradient oscillation** | Искусственное создание колебаний path_cost (резкое повышение/понижение) для дестабилизации маршрутизации и переполнения gradient-table | MGR gradient table | Периодическая рассылка `PotMsg::Gradient` с противоположными cost для одного destination | **Слой 1:** `gradient_update_rate_limit` — лимит на число обновлений cost за единицу времени. **Слой 2:** `GradientVelocitySensor`: отслеживает скорость изменения cost. Резкие колебания (oscillation) → флаг. **Слой 3:** Игнорирование обновлений от источника на срок `gradient_ignore_ttl` |

#### Концепция защиты Mycerus для категории B

**Обнаружение (Слой 2):**

- `E2ETrackingSensor`: использует `ReportE2EDelivery` (уже есть в этапе 14–16). Сравнивает предсказанный path_cost с фактическим. Систематическое расхождение в одном направлении → аномалия.
- `GradientVelocitySensor`: отслеживает скорость изменения path_cost к каждому destination. Резкое падение (ложный shortcut) или застревание — сигнал.
- Формула аномалии (адаптивный baseline):

```javascript
  anomaly_score = |metric(t) − median(metric, window)| / (MAD(metric, window) + ε)
```

где `window` — последние N контактов, `MAD` — медианное абсолютное отклонение. Порог — 3×MAD.

**Контрмера (Слой 3 — пенициллин):**

- Таргетинг **идентичности и поведения**, не payload:
- Отказ в relay: узел в состоянии `degraded` не пересылает чужие bundle'ы.
- Игнорирование gradient-обновлений от него в MGR.
- Снижение copies при Spray (если копии идут через него — уменьшается число передаваемых экземпляров).
- `PotMsg::Threat` типа `routing_anomaly` содержит: (target_key, anomaly_type, evidence_hash, timestamp, TTL).

**Гиперчувствительность (Слой 4):**

- Только при `quorum_threshold=2` подтверждённых сенсора.
- Действие: `PotMsg::Quarantine` — полный отказ в relay и игнорирование gradient'ов на срок `threat_ttl_sec`.
- Предохранитель: `quarantine_max_scope=0.1` — не более 10% узлов флота могут быть одновременно в quarantine. При превышении — глобальная пауза на новые quarantine до освобождения слотов.

### Категория C. Атаки на ресурсы и доступность

*Атакующий исчерпывает буфер, CPU или пропускную способность узлов.*

| ID | Угроза | Описание | Целевой компонент | Вектор атаки | Защита (слой иммунитета) |
| --- | --- | --- | --- | --- | --- |
| **C1** | **Bundle flooding** | Спам ложными bundle'ами для переполнения bundle-store жертвы | Bundle store (BPv7), local_resources | Генерация bundle'ов с произвольным payload на максимальный размер | **Слой 1:** Rate limiting на приём bundle'ов от одного соседа за контакт. **Слой 2:** `ResourcePressureSensor`: мониторинг fill-ratio bundle-store. **Слой 3:** При превышении threshold — отказ в приёме новых bundle'ов от этого соседа (не глобально, а точечно) |
| **C2** | **Computation DoS** | Спам challenge-response для исчерпания CPU на Ed25519-проверках | SNS/SRE, CPU | Массовая инициация SNS-handshake без намерения передавать данные | **Слой 1:** Rate limiting на challenge-response (exponential backoff при частых запросах от одного ключа). **Слой 2:** `HandshakeRateSensor`: отклонение частоты handshake от медианы. **Слой 3:** Временный отказ в handshake с ключом — «септа закрывает пору» |
| **C3** | **Gradient table poisoning** | Фальшивые gradient-обновления для переполнения таблицы cost или создания ложных маршрутов | MGR gradient table | Массовая рассылка `PotMsg::Gradient` с уникальными dst/cost | **Слой 1:** Лимит на число обновлений от одного соседа за единицу времени. **Слой 2:** `GradientPlausibilitySensor`: cost должен коррелировать с известной топологией (не может быть <0, не может резко упасть без нового контакта). **Слой 3:** Игнорирование обновлений от нарушителя + Threat-bundle |
| **C4** | **Contact starvation** | Блокирование легитимных контактов через флуд короткими встречами, чтобы у жертвы не осталось времени на обмен с настоящими соседями | POT contact scheduling | Постоянные короткие «встрелы» (probe-and-drop) от Sybil-узлов | **Слой 2:** `ContactQualitySensor`: измеряет ratio полезных контактов (с передачей bundle'ов) к общему числу. Резкое падение — тревога. **Слой 3:** Приоритизация контактов по исторической полезности; degraded-узлы получают минимальный слот |
| **C5** | **Immune plane flooding** | Атакующий заваливает сеть валидными (подписанными) Threat-бундлами против разных целей, исчерпывая CPU на проверках, память на revocation-листах, CPU на пересчёте FSM | Immune plane, CPU, memory | Массовая генерация подписанных Immune Block (тип 202) от скомпрометированного или Sybil-сенсора | **Слой 1:** Rate limiting на приём Immune Block per-sensor. **Слой 2:** `ImmunePressureSensor`: мониторинг вычислительной нагрузки immune plane. **Слой 3:** Бюджет immune-вычислений per contact; приоритет обработки по репутации сенсора (положительная rep → первоочередной); превышение бюджета → отбрасывание блоков от низкорепутационных сенсоров |
| **C6** | **Storage exhaustion** | Переполнение bundle-store валидными подписанными bundle'ами с максимальным размером, которые невозможно отбросить по формальным признакам | Bundle store (BPv7), local_resources | Генерация bundle'ов с валидной подписью, легитимным destination, но бесполезным payload (например, случайные данные) | **Слой 1:** `bundle_size_limit` + `bundle_ttl_limit` — жёсткие ограничения на размер и время жизни. **Слой 2:** `StoragePressureSensor`: мониторинг fill-ratio. При fill > threshold — приоритизация по age и доставляемости. **Слой 3:** Eviction: старые bundle'ы с низкой доставляемостью удаляются first. **Слой 5:** Периодическая чистка (garbage collection) в фоне |

#### Концепция защиты Mycerus для категории C

**Обнаружение (Слой 2):**

- `ResourcePressureSensor`: триггерится по `local_resources.fill_ratio > threshold`. Измеряет вклад каждого соседа в нагрузку.
- `HandshakeRateSensor`: адаптивный baseline по частоте SNS-handshake. Если один ключ запрашивает handshake чаще, чем медиана + 3×MAD — флаг.
- `ContactQualitySensor`: для каждого соседа отслеживается `useful_contacts / total_contacts`. Полезный контакт = передан хотя бы один bundle или gradient. Падение ниже квантиля — аномалия.

**Контрмера (Слой 3 — пенициллин):**

- **Селективное ограничение**, а не глобальное отключение:
- Bundle flooding → приёмное окно от конкретного ключа сокращается до 1 bundle/контакт.
- Computation DoS → exponential backoff на handshake для этого ключа.
- Gradient poisoning → hard limit на число принимаемых gradient-обновлений от ключа за контакт.
- Все контрмеры с TTL: по истечении — автоматическое восстановление (`probation`).

**Контрмера для C5 (Слой 3 — пенициллин):**
- **Rate limiting per-sensor:** не более `immune_block_per_sensor_limit` (например, 10) Immune Block'ов от одного сенсора за контакт. Превышение → остальные отбрасываются без проверки подписи.
- **Бюджет immune-вычислений:** на каждый контакт выделяется лимит CPU/времени на обработку Immune Block'ов. При исчерпании — оставшиеся блоки откладываются или отбрасываются.
- **Приоритет по репутации:** блоки от сенсоров с `rep > 0` обрабатываются первыми; блоки от сенсоров с негативной/нулевой репутацией — последними или игнорируются.
- Threat'ы от сенсоров без достаточной репутации не участвуют в кворуме.

**Гиперчувствительность (Слой 4):**
- Только при массовой атаке (кворум сенсоров фиксирует одновременное давление на ≥2 узлах).
- Действие: глобальный rate limiting на приём bundle'ов от незнакомых ключей (graceful degradation).

### Категория D. Атаки на доверие и консенсус

*Атакующий подрывает механизм принятия решений: ложные тревоги, захват сенсоров, манипуляция кворумом, коллюзия.*

Это **самая опасная категория**, потому что направлена против самой иммунной системы. Успешная атака здесь заставляет сеть уничтожить себя.

| ID | Угроза | Описание | Целевой компонент | Вектор атаки | Защита (слой иммунитета) |
| --- | --- | --- | --- | --- | --- |
| **D1** | **False alarm (Bad-mouthing)** | Легитимный узел (или скомпрометированный) инициирует ложную тревогу `PotMsg::Threat` против честного конкурента | Immune plane, Sensor network | Подписанный, но ложный Threat-bundle с искажёнными evidence | **Слой 5:** Репутация сенсоров. Каждый узел ведёт таблицу: сенсор → (подтверждённые тревоги, ложные тревоги). Сенсор с негативной историей исключается из кворума. **Слой 4:** Кворум N=2 обязателен для HR; один сенсор = только `watch` |
| **D2** | **Sensor capture** | Атакующий захватывает узел, который был доверенным сенсором, и использует его для генерации правдоподобных ложных сигналов | Immune plane | Node capture + сохранение сенсорного статуса | **Слой 2:** Детектор рассогласования: если сенсор A поднимает тревогу, а сенсоры B и C в том же регионе не фиксируют аномалии — вероятность ложной тревоги растёт. **Слой 5:** Репутация сенсора деградирует; при обнулении — исключение |
| **D3** | **Quorum manipulation** | Атакующий создаёт N Sybil-сенсоров, чтобы формировать кворум против произвольных узлов | Immune plane, SNS | Sybil + ложные Threat'ы | **Слой 1:** Сенсорный статус привязан к истории (не к identity). Новый узел не может стать сенсором без «вызревания». **Слой 5:** Репутация вычисляется по времени и точности; Sybil'ы не успевают набрать вес. **Слой 2:** Топологическое разнообразие (см. D5) |
| **D4** | **Self-promotion** | Узел систематически занижает репутацию конкурентов и завышает свою, чтобы монополизировать маршрутизацию | MGR, Vironet fitness | Искажение gradient'ов, ложные negative report о конкурентах | **Слой 2:** `ReputationConsistencySensor`: сравнивает заявленную репутацию с наблюдаемым поведением. **Слой 5:** Fitness Vironet включает штраф за ложные отказы в доверии. Геном, генерирующий много ложных тревог, получает низкий fitness |
| **D5** | **Collusion** | Два или более легитимных узла с разными ключами сговариваются и подтверждают ложную тревогу друг друга, формируя «легитимный» кворум | Immune plane, Quorum | Сговор между реальными узлами с положительной репутацией | **Слой 2:** **Топологическое разнообразие сенсоров:** два сенсора не считаются независимыми для кворума, если они видят одних и тех же соседей (shared neighbor set > threshold). **Слой 5:** Репутация обоих сенсоров падает при выявлении коллюзии |
| **D6** | **Collusion ring** | Организованное кольцо из N≥3 скомпрометированных сенсоров, которые циклически подтверждают ложные тревоги друг друга, создавая sustained ложный кворум | Immune plane, Quorum, Reputation | Сговор через out-of-band канал; сенсоры имеют положительную репутацию и топологическое разнообразие | **Слой 2:** `CollusionPatternSensor`: анализирует граф подтверждений тревог. Если подмножество сенсоров только подтверждают друг друга (closed loop) — флаг. **Слой 5:** Репутация кольца деградирует как единое целое. При выявлении — массовый strike. **Слой 4:** Приостановка кворума для подозрительного кластера до проверки |

#### Концепция защиты Mycerus для категории D

**Обнаружение (Слой 2):**

- `QuorumConsistencySensor`: сравнивает тревоги от разных сенсоров. Если тревога поднята одним сенсором, а соседние не подтверждают — флаг на `false_alarm`.
- `ReputationCorrelationSensor`: коррелирует репутацию узла (как сенсора) с объективными метриками: доставляемость через него, количество подтверждённых vs отклонённых тревог.
- **Топологическая независимость (коллюзия):** для кворума требуется, чтобы пересечение множеств соседей у двух сенсоров было < `shared_neighbor_threshold` (например, 50%). Если сенсоры видят одно и то же — они не независимы. Биологически: иммунная система не считает два сигнала от одного типа клеток независимыми подтверждениями.

**Контрмера (Слой 3 — пенициллин):**

- **Не изолируем жертву тревоги, а деградируем сенсор:**
- При ложной тревоге: сенсор получает strike в таблице репутации.
- При ≥3 ложных тревогах: сенсор исключается из кворума на срок `sensor_penalty_ttl`.
- При коллюзии: оба сенсора получают strike, кворум аннулируется.
- Его собственные Threat'ы игнорируются, но он остаётся легитимным узлом для relay.
- Это и есть **autoimmune guard**: система наказывает ложные срабатывания сильнее, чем пропуск реальной угрозы (асимметричный штраф).

**Гиперчувствительность (Слой 4):**

- **Никогда не активируется по сигналам только одного сенсора.**
- Минимальный кворум для HR: N=2 сенсора с положительной репутацией (rep > 0) и топологически независимых.
- Для массовых атак: если ≥20% узлов поднимают тревогу одновременно — это сигнал глобальной аномалии (например, сбой сети, а не атака), и HR блокируется.

**Иммунная память (Слой 5):**

- Таблица репутации сенсоров — часть локального состояния, но агрегированные метрики (процент ложных тревог по типу) записываются в `immune.known_threats` генома.
- При эволюции Vironet fitness включает:

```javascript
  fitness += attack_resilience
  fitness -= false_positives × penalty_weight
  fitness -= false_negatives × lighter_penalty_weight
```

Асимметрия штрафов предотвращает параноидальную эволюцию.

### Категория E. Атаки на инфраструктуру и физический уровень

*Атакующий действует вне протокола: глушение, физический захват, разрушение узлов, временные атаки.*

| ID | Угроза | Описание | Целевой компонент | Вектор атаки | Защита (слой иммунитета) |
| --- | --- | --- | --- | --- | --- |
| **E1** | **Selective jamming** | Глушение радиоканала в момент контакта конкретных узлов (умное глушение, а не широкополосное) | POT CLA (radio/WiFi) | Анализ трафика, точечное глушение при обнаружении handshake | **Слой 0:** Избыточность путей — jamming одного канала не обрушивает маршрут. **Слой 2:** `ContactPatternSensor`: необъяснимые пропуски ожидаемых контактов (по истории) в присутствии соседа — сигнал глушения. **Слой 3:** Переключение на альтернативный CLA (например, с WiFi на BLE) |
| **E2** | **Node capture** | Физический захват устройства с извлечением ключей, credentials, состояния gradient-table | Весь стек | Физический доступ | **Слой 1:** Ключи в encrypted storage, tamper-evident. **Слой 5:** Ревокация ключа через Threat-bundle от соседей (если захваченный узел «замолкает» или начинает вести себя аномально). **Слой 0:** Redundancy — потеря одного узла не критична |
| **E3** | **Targeted isolation** | Умышленное отключение или изоляция мостового узла для разделения сети на сегменты | MyceliumNet topology | Физическое уничтожение, jamming, или компрометация всех маршрутов через узел | **Слой 0:** Анастомозы — альтернативные пути. **Слой 2:** `BridgeLossSensor`: мониторинг числа путей между регионами. Резкое падение — тревога. **Слой 4:** Активация backup-маршрутов (эвакуация на резервные пути) |
| **E4** | **Time desynchronization** | Манипуляция временными метками узла для нарушения TTL, epoch, freshness-nonce | SNS, MGR, Immune plane | Spoofed NTP, поддельные timestamp'ы в beacon'ах | **Слой 1:** Logical clocks (epoch + monotonic counter) для ordering; wall-clock только для TTL. **Слой 2:** `TimeConsistencySensor`: медианное сетевое время по соседям в окне контактов, отклонения >3×MAD — отбрасывание. **Слой 3:** Игнорирование обновлений с невалидным временем |

#### Концепция защиты Mycerus для категории E

**Обнаружение (Слой 2):**

- `BridgeLossSensor`: периодически вычисляет edge connectivity между регионами (по gradient-table). Резкое падение — сигнал targeted isolation.
- `ContactPatternSensor`: если узел A historically контактировал с B в 90% случаев, а теперь 0% в течение окна — аномалия (jamming или захват).
- `TimeConsistencySensor`: **медианное сетевое время по соседям**, а не глобальное или локальное wall-clock.
- Каждый узел собирает timestamp'ы от N соседей в окне контактов.
- Берёт медиану. Отклонения >3×MAD — отбрасываются.
- Это работает в DTN, потому что каждый узел всё равно видит только своих соседей.
- Wall-clock используется **только для TTL** (грубая оценка устаревания) и то с осторожностью.
- **Logical clocks** (epoch, monotonic counter в SRE) используются для ordering и freshness.

**Контрмера (Слой 3 — пенициллин):**

- Time desync → игнорирование сообщений с timestamp'ом вне допустимого окна (не изоляция узла, а фильтрация «протухших» данных).
- Selective jamming → переключение на резервный CLA (Channel Layer Adapter), если такой доступен.
- Node capture → распространение `PotMsg::Revoke` с ключом захваченного узла (revocation-at-contact).

**Гиперчувствительность (Слой 4):**

- Targeted isolation моста → активация **споруляции**: backup-геном с альтернативной топологией (если есть) или emergency broadcast по всем доступным CLA для восстановления связности.
- Это единственный случай, когда HR-ответ не требует кворума — потеря моста между регионами критична, и сеть должна реагировать немедленно. Но действие ограничено: только активация резервных путей, не изоляция.

**Иммунная память (Слой 5):**

- `known_threats` включает шаблоны: «потеря моста», «jamming pattern», «time desync».
- При повторной встрече с известным шаблоном реакция ускоряется: bypass кворума для известных critical-паттернов.

### Категория F. Атаки на Vironet / Evolution plane

*Атакующий нацелен не на трафик, а на сам механизм эволюции: подмена фитнеса, захват пула геномов, провокация отката.*

Эта категория **уникальна для Mycerus**: большинство DTN-проектов не имеют эволюционирующего плоскости, поэтому атаки на неё не рассматриваются. Для Mycerus это критично — компрометация Vironet = компрометация всей политики маршрутизации.

| ID | Угроза | Описание | Целевой компонент | Вектор атаки | Защита (слой иммунитета) |
| --- | --- | --- | --- | --- | --- |
| **F1** | **Fitness poisoning** | Атакующий подстраивает условия прогона (трасса, нагрузка, расположение узлов) так, чтобы его геном получал завышенный fitness, хотя на реальной сети он хуже | Vironet fitness, trace-replay | Манипуляция входными данными эволюции: выбор «удобной» трассы, подделка метрик | **Слой 2:** `FitnessPlausibilitySensor`: сравнение fitness на разных трассах. Расхождение > threshold → тревога. **Слой 5:** Обязательная кросс-валидация: геном должен показать приемлемый fitness на ≥2 независимых трассах перед принятием |
| **F2** | **Genome pool capture** | Sybil-узлы наводняют пул геномов своими версиями, вытесняя разнообразие и продвигая уязвимую политику | Vironet genome pool | Массовая генерация валидных геномов с близкими к лидеру fitness, но встроенными backdoor | **Слой 1:** creator_signature + проверка происхождения генома. **Слой 5:** Diversity guard в fitness: бонус за энтропию популяции геномов. Constraints ограничивают долю геномов от одного creator |
| **F3** | **Evolutionary drift** | Не атака, но риск: медленное смещение constraints через серию легитимных мутаций, которая ослабляет защиту | Vironet constraints | Естественная эволюция без давления со стороны атак | **Слой 5:** «Вакцинация» — обязательный прогон в attack harness (этап 19) перед принятием генома. Constraints с жёсткими floor'ами на immune-параметры |
| **F4** | **Rollback manipulation** | Атакующий провоцирует откат к старому уязвимому геному (например, через DDoS, который новый геном переживает хуже) | Vironet rollback | Массированная атака, направленная на то, чтобы текущий лидер показал низкий fitness и откатился | **Слой 5:** Rollback guard: минимальное время жизни генома перед откатом; «вызревание» — прогон под attack harness. Откат на геном без immune-блока запрещён constraints |
| **F5** | **Adaptive genome** | Атакующий эволюционирует геном, который адаптируется под его поведение: снижает чувствительность сенсоров к его атакам, ослабляет constraints | Vironet genome, constraints | Итеративная эволюция генома в sandbox'е атакующего с подбором мутаций, которые минимизируют detection его атак | **Слой 2:** `GenomeBehaviorSensor`: сравнивает заявленные параметры immune plane с фактическим поведением сети. Расхождение → флаг. **Слой 5:** Constraints с жёсткими floor'ами на immune-параметры (min_sensor_count, max_quorum_ttl). Эволюция не может опустить их ниже floor. **Слой 4:** Прогон в attack harness перед принятием — адаптивный геном провалит сценарии J–L |

#### Концепция защиты Mycerus для категории F

**Обнаружение (Слой 2):**

- `FitnessPlausibilitySensor`: сравнивает fitness одного генома на разных трассах (HT2009 vs school). Формализация:
  ```
  variance_ratio = MAD(fitness_genome) / MAD(fitness_population)
  flag if variance_ratio > threshold (например, 2.0)
  ```
  где `MAD(fitness_genome)` — медианное абсолютное отклонение fitness данного генома по трассам, `MAD(fitness_population)` — то же для популяции baseline-геномов. Флаг срабатывает только если геном вариативнее, чем типичный представитель популяции — иначе сенсор будет ложно срабатывать на нормальных геномах, которые просто по-разному работают на разных трассах.
- `PoolDiversitySensor`: мониторит энтропию Шеннона популяции геномов. Резкое падение — сигнал pool capture.

**Контрмера (Слой 3 — пенициллин):**

- Fitness poisoning → отклонение генома на этапе кросс-валидации. Не изоляция узла, а отказ принять его геном в пул.
- Genome pool capture → constraints: `max_genome_share_per_creator = 0.2` — не более 20% пула от одного creator.

**Гиперчувствительность (Слой 4):**

- Rollback manipulation → hard limit: геном без immune-блока не может быть откатом. Это предохранитель от отката к «дои­ммунной» эпохе.

**Иммунная память (Слой 5):**

- `known_threats` включает шаблоны: «fitness_poisoning_trace", "pool_entropy_drop", "rollback_to_vulnerable".
- Constraints фиксируют floor'ы для immune-параметров: `quorum_threshold ≥ 2`, `quarantine_max_scope ≤ 0.1`, `sensor_penalty_ttl ≥ 3600`.

## 5. Биологические аналоги: как пенициллин и иммунитет гриба ложатся на модель

| --- | --- | --- |
| **Септы с порами** | SNS handshake + selective relay | Обмен разрешён, но через контролируемую «пробку». Пора закрывается при угрозе (Worhonin body), но не герметично — иначе мицелий умрёт от изоляции |

| **РНК-интерференция** | Adaptive MAD-sensor | Распознаёт «чужую нуклеиновую кислоту» = отклонение от собственного baseline. Не константа, а калибровка на норму |
| **Гиперчувствительный ответ (HR)** | Кворум + quarantine + bridge-hostage | Локальная гибель клеток ради спасения целого. Требует сигнала от нескольких независимых источников. | **Споруляция** | Backup-геном, emergency routing, state replication | При гибели субстрата сеть сохраняется через «споры» — резервные копии состояния и альтернативные маршруты |
| **Вакцинация (аттенуированный патоген)** | Attack harness в песочнице Vironet | Ослабленные атаки на трассах для «прививки» геномов. Удачные защитные стратегии записываются в `known_threats` |
| **Резистентность (супербактерии)** | Адаптация атакующего к контрмерам | Мутация генома защиты (Vironet) противостоит адаптации атак. Ротация ключей и ротация сенсорных порогов предотвращают «привыкание» |

## 6. Формат Immune Block (тип 202)

Threat-факты, кворумные приказы и отзывы ключей передаются через **отдельный Extension Block типа 202 — Mycerus Immune Block**. Это не подтип MEB (тип 200), а самостоятельный тип блока.

**Почему не MEB-подтип:**
- MEB v0.1.1 имеет фиксированные ключи 1–10 и не предусматривает поле `subtype`. Расширение MEB под иммунную систему размыло бы его назначение.
- Иммунная система имеет другой жизненный цикл: TTL валидности, не дедлайн доставки; приоритет обработки отличается от маршрутной политики; старые узлы должны отбрасывать блок чисто.
- Отдельный тип 202 даёт собственное пространство подтипов и правил обработки.

```
Extension Block (тип 202 — Mycerus Immune Block)
├── subtype: uint8
│   ├── 1 = Threat        — подписанное утверждение от сенсора
│   ├── 2 = Quarantine    — приказ кворума (>=2 независимых сенсора)
│   ├── 3 = Revoke        — отзыв ключа (creator или кворум)
│   └── 4 = Reroute       — сигнал rerouting campaign (bridge-hostage)
├── payload (CBOR):
│   ├── target_key: bytes       (Ed25519 public key)
│   ├── threat_type: string     (enum: identity_spoof, routing_anomaly, stale_gradient,
│   │                            resource_abuse, false_alarm, immune_flood, ...)
│   ├── evidence_hash: bytes    (SHA-256 of evidence)
│   ├── timestamp: uint64       (epoch seconds)
│   ├── ttl_sec: uint32         (окно валидности утверждения, не дедлайн доставки)
│   ├── sensor_key: bytes       (Ed25519 public key сенсора, для Threat)
│   ├── sensor_signature: bytes (Ed25519 signature над всеми полями)
│   └── quorum_signatures: array<bytes>  (для Quarantine: подписи всех сенсоров кворума)
└── flags: discard-if-not-processed
```

**Семантика:**
- **Threat (subtype 1)** — не **приказ**, а **подписанное утверждение**: «узел X с ключом K совершил действие типа T в момент t».
- **Quarantine (subtype 2)** — приказ кворума, действует немедленно (если target не является local bridge с активным rerouting).
- **Revoke (subtype 3)** — отзыв ключа. Распространяется как обычный bundle; каждый узел проверяет подпись issuer и добавляет ключ в локальный revocation-лист.
- **Reroute (subtype 4)** — сигнал запуска rerouting campaign при bridge-hostage (см. раздел 8).

**Обработка:**
- Каждый узел хранит локальный revocation-лист и проверяет его при каждом SNS-handshake.
- `ttl_sec` — окно валидности утверждения. После истечения узел может быть реабилитирован через `probation`.
- SNS-handshake становится не только «свой/чужой», но и «не отозван ли ты».
- **Rate limiting:** приём Immune Block per-sensor ограничен (см. категорию C5). Приоритет: блоки от сенсоров с положительной репутацией обрабатываются первыми.

```rust
pub struct QuorumEngine {
    pub threshold: u32,            // из генома: quorum_threshold (минимум 2, invariant)
    pub min_sensor_rep: f64,       // из генома: минимальная репутация для участия
    pub shared_neighbor_threshold: f64, // из генома: threshold топологической зависимости
    pub neighbor_window: usize,    // из генома: число последних контактов для окна
    pub sparse_fallback_k: usize,  // из генома: минимальное число соседей для fallback
    pub sensor_min_age: Duration,  // минимальный возраст сенсора для fallback (антиспам)
}

impl QuorumEngine {
    // Проверяет, образуют ли события валидный кворум
    pub fn evaluate(&self, events: &[SensorEvent]) -> QuorumResult {
        // 1. Фильтрация: только сенсоры с rep > min_sensor_rep
        // 2. Топологическая независимость:
        //    Для каждой пары сенсоров (A, B):
        //      neighbors_A = соседи A за последние neighbor_window контактов
        //      neighbors_B = соседи B за последние neighbor_window контактов
        //      shared = |neighbors_A ∩ neighbors_B|
        //      normalized = shared / min(|neighbors_A|, |neighbors_B|)
        //      Fallback для разреженных трасс:
        //        Если |neighbors_A| < sparse_fallback_k И |neighbors_B| < sparse_fallback_k
        //           И age(A) > sensor_min_age И age(B) > sensor_min_age:
        //           → считать независимыми (только для зрелых разреженных сенсоров)
        //      Иначе если normalized > shared_neighbor_threshold:
        //         → исключить из кворума (не независимы)
        // 3. Если осталось ≥ threshold событий против одного target → QuorumConfirmed
        // 4. Иначе → QuorumDenied
    }
}
```

### 7.7. Differential Privacy для сенсоров

Сенсоры анализируют поведение, но метаданные тоже чувствительны. Если `ContactRateSensor` публикует, что «Алиса шлёт 50 сообщений в день Бобу» — это уже утечка информации.

**Решение:** каждый сенсор добавляет Laplace noise к `score` перед включением в `SensorEvent`:

```rust
pub struct PrivateSensor {
    base_sensor: Box<dyn Sensor>,
    epsilon: f64,  // privacy budget (из генома: sensor_epsilon, invariant)
}

impl Sensor for PrivateSensor {
    fn on_bundle(&mut self, event: &BundleEvent) -> Vec<SensorEvent> {
        let mut events = self.base_sensor.on_bundle(event);
        for e in &mut events {
            // Добавляем Laplace noise к score
            let noise = laplace_noise(1.0 / self.epsilon);
            e.score = (e.score + noise).max(0.0);
        }
        events
    }
}
```

**Параметр `epsilon`:**
- Часть генома, но является **invariant** — эволюция не может его мутировать.
- Меньше epsilon = больше privacy, но сенсоры менее точные. Нужен баланс.
- Рекомендуемое значение: `epsilon = 1.0` (стандартный privacy budget).

**Trade-off:** DP снижает точность сенсоров → более высокие пороги CUSUM → медленнее detection. Это создаёт `privacy_latency_tradeoff`, который Vironet не может оптимизировать (epsilon invariant), но может адаптировать `cusum_h`.

## 8. Конечный автомат доверия (Trust FSM)

```
                              ┌─────────────────────────────────────────┐
                              │                                         │
                              ▼                                         │
  ┌─────────┐    watch (1 sen)    ┌─────────┐   degraded (2 sen)  ┌───────────┐
  │ TRUSTED │ ───────────────────▶│  WATCH  │ ──────────────────▶│ DEGRADED  │
  │  (полное│                     │(logging)│                    │(no relay, │
  │ участие)│◀────────────────────│  TTL=h  │◀───────────────────│no gradient│
  └─────────┘   чистая история    └─────────┘   истечение TTL    │  TTL=h-d  │
       ▲                            │                             └─────┬─────┘
       │                            │                                   │
       │                            │ probation                         │ quarantine
       │                            │ (ограниченное участие,            │ (2 sen again)
       │                            │  усиленный мониторинг)            │
       │                            │  TTL=d                           │
       │                            │                                   │
       │                            │         ┌──────────────────────┐  │
       │                            └────────▶│  BRIDGE-HOSTAGE      │  │
       │                                      │  (rerouting campaign)│◀─┘
       │                                      │                      │
       │                                      │  1. forced degraded  │
       │                                      │  2. reroute signal   │
       │                                      │  3. build bypass     │
       │                                      │  4. quarantine OK    │
       │                                      └──────────────────────┘
       │                                                                 │
       │                                                                 ▼
       │                            ┌──────────────────┐         ┌───────────┐
       └────────────────────────────│   PROBATION      │◀────────│QUARANTINED│
           истечение probation       │ (ограниченное    │         │(изоляция) │
           чистая история            │  участие)        │         │  TTL=d    │
                                     │  TTL=d           │         └───────────┘
                                     └──────────────────┘
```

**Правила:**
- Переход `trusted → watch`: один сенсор с rep>0 поднял тревогу. Действие: логирование, без ограничений. TTL: часы.
- Переход `watch → degraded`: кворум N=2 топологически независимых сенсора с rep>0. Действие: пауза relay, игнор gradient, снижение copies. TTL: часы–сутки.
- Переход `degraded → quarantined`: повторный кворум (новые сигналы, не старые).
  - **Bridge-hostage guard:** если узел является **local bridge** (см. раздел 8.1), quarantine не применяется немедленно. Вместо этого:
    1. Узел переводится в **forced degraded** с усиленным мониторингом.
    2. Запускается **rerouting campaign**: сеть распространяет `Immune Block subtype 4 (Reroute)`, принимает временное снижение доставляемости и строит альтернативные пути (анастомозы, споруляция, emergency CLA).
    3. Как только альтернативный путь построен и проверен (появился gradient с приемлемым cost к ранее изолированному региону) — bridge-hostage guard снимается.
    4. После снятия guard применяется обычный quarantine.
  - Bridge-hostage — это **не привилегия**, а **отсрочка с условием**. Иначе мост становится неприкосновенным.
- Переход `quarantined → probation`: истечение TTL. Действие: ограниченное участие, усиленный мониторинг. TTL: дни.
- Переход `probation → trusted`: чистая история (нет новых тревог за окно). Действие: полное восстановление.
- **Предохранитель 1:** `quarantine_max_scope = 0.1`. Если ≥10% узлов уже в quarantine — новые quarantine блокируются до освобождения слотов.
- **Предохранитель 2 (bridge-hostage):** local bridge-узлы не подвергаются немедленному quarantine без rerouting campaign.

### 8.1. Local bridge estimate

Узел в DTN **не знает глобальной топологии**. У него есть только локальная аппроксимация — собственная gradient-table. Поэтому «мост» — это не глобальное свойство, а **local bridge estimate**:

```
local_bridge_estimate(target) = true  if
    ∀ destination D в gradient-table:
        единственный известный next_hop к D — target
    ∧ удаление target из gradient-table увеличивает число
      недостижимых destination
```

Это **локальная эвристика**, не претендующая на глобальность. Узел может быть мостом для одного региона и не быть мостом для другого. Разные узлы могут иметь противоречивые оценки. Это нормально — FSM принимает решение локально, и сеть сходится через rerouting campaign.

### 8.2. Immune Shock Detector (cytokine storm guard)

В биологии cytokine storm — иммунная система перегибает палку и убивает организм. В Mycerus аналог: если 20% сети одновременно в quarantine из-за ложной тревоги — сеть коллапсирует.

**Immune Shock Detector** — глобальный предохранитель (не FSM-состояние, а системный монитор):

```rust
pub struct ImmuneShockDetector {
    quarantine_rate_threshold: f64,  // например, 0.05 (5% за 1 контакт)
    global_pause_duration: Duration, // например, 1 час
}

impl ImmuneShockDetector {
    pub fn check(&mut self, fsm_table: &FSMTable, recent_changes: usize) -> Option<ShockResponse> {
        let total_nodes = fsm_table.len();
        let quarantined = fsm_table.count_quarantined();
        let rate = (quarantined as f64 / total_nodes as f64) / recent_changes as f64;
        
        if rate > self.quarantine_rate_threshold {
            // Cytokine storm detected
            Some(ShockResponse {
                action: ShockAction::GlobalPause,
                duration: self.global_pause_duration,
                reset_cusum: true,
                freeze_new_quarantines: true,
            })
        } else {
            None
        }
    }
}
```

**При срабатывании:**
1. **Global pause:** новые quarantine блокируются на `global_pause_duration`.
2. **CUSUM reset:** все CUSUM-накопители сбрасываются (стирается история отклонений).
3. **Freeze:** существующие quarantine не отменяются, но новые не применяются.
4. **Log:** событие записывается в `known_threats` как «immune_shock».

**Почему не отменяем существующие quarantine:** это могло бы восстановить атакующих. Pause только *приостанавливает* эскалацию.

**Инвариант:** `quarantine_max_scope ≤ 0.1` — не более 10% узлов в quarantine. Если приближаемся — Shock Detector срабатывает раньше.

### 8.3. Circuit Breaker (auto-rollback immune-параметров)

Immune Shock Detector ловит всплеск quarantine, но не ловит **медленную деградацию генома**: плохая мутация делает сенсоры гиперчувствительными, immune debt копится медленно, shock не срабатывает, а откат генома ждёт эпохи Vironet — которая в разреженной сети длится неделями.

**Circuit Breaker:**

```rust
pub struct ImmuneCircuitBreaker {
    debt_threshold: f64,       // immune_debt_rate порог (например, 0.05)
    debt_window: usize,        // окно в контактах (например, 100)
    rollback_target: Genome,   // последний known-good immune-блок
}

impl ImmuneCircuitBreaker {
    pub fn check(&mut self, debt_history: &[f64]) -> Option<RollbackAction> {
        if debt_history.len() < self.debt_window {
            return None;
        }
        
        let recent_debt = &debt_history[debt_history.len() - self.debt_window..];
        let avg_debt = recent_debt.iter().sum::<f64>() / recent_debt.len() as f64;
        
        if avg_debt > self.debt_threshold {
            // Медленная деградация — немедленный откат immune-параметров
            Some(RollbackAction {
                target_genome: self.rollback_target.clone(),
                preserve_memory: true,  // known_threats сохраняются
                reset_sensors: true,    // CUSUM сбрасываются
            })
        } else {
            None
        }
    }
}
```

**Почему откат immune, а не всего генома:**
- Маршрутизация (MGR, Vironet) может работать нормально, пока immune plane деградирует.
- Откат только immune-блока быстрее и безопаснее.
- `preserve_memory = true` — known_threats не сбрасываются, чтобы не потерять иммунную память.

**Пенициллин не должен ждать разрешения, чтобы отменить сам себя.**

## 10. Требования к реализации (этапы 17–20)

### Этап 17. Сенсоры (Sensors)

**Что строим:**

- `SNSAnomalySensor`: failed challenge-rate per neighbor
- `BeaconConsistencySensor`: genome_id vs key fingerprint
- `GradientVelocitySensor`: anomaly_score по MAD для path_cost
- `E2ETrackingSensor`: сравнение predicted vs actual delivery (через ReportE2EDelivery)
- `ResourcePressureSensor`: fill_ratio bundle-store
- `HandshakeRateSensor`: handshake frequency per key
- `ContactQualitySensor`: useful_contacts / total_contacts
- `QuorumConsistencySensor`: cross-sensor validation + топологическая независимость
- `TimeConsistencySensor`: медианное сетевое время по соседям
- `FitnessPlausibilitySensor`: cross-trace fitness variance (для F1)
- `PoolDiversitySensor`: энтропия пула геномов (для F2)

**Критерий приёмки:**

- На 3 реальных трассах (HT2009, InVS15, school) ложные срабатывания каждого сенсора < 5% при отсутствии атаки.
- Шум стенда ±0.15 DR не приводит к превышению порога.
- Сенсоры D (кворум) не срабатывают при ложной тревоге одного сенсора.
- **Метрика detection latency:** время от начала атаки до первого срабатывания сенсора (для CUSUM — число bundle'ов до CUSUM > h).

### Этап 18. Протокол ответа (Response Protocol)

**Что строим:**

- Immune Block тип 202 с подтипами: Threat (1), Quarantine (2), Revoke (3), Reroute (4).
- Threat: `{ target_key, threat_type, evidence_hash, timestamp, ttl_sec, sensor_key, sensor_signature }`
- Quarantine: `{ target_key, quorum_signatures[], ttl }`
- Revoke: `{ revoked_key, reason, replacement_key?, timestamp, ttl, issuer_signature }`
- Trust FSM (6 состояний) в каждом узле с bridge-hostage guard + rerouting campaign.
- Локальный revocation-лист с TTL валидности.
- SNS-handshake проверяет revocation-лист: «не отозван ли ты?»
- Sensor API в терминах MGR/SNS/POT событий.
- Rate limiting и бюджет immune-вычислений per contact.

**Критерий приёмки:**

- Threat-bundle от одного сенсора → цель переходит в `watch`.
- Threat-bundle от кворума (2 независимых сенсора) → цель переходит в `degraded`.
- Повторный кворум → `quarantined` (если не local bridge) или запуск rerouting campaign + `forced degraded` (если local bridge).
- Ложная тревога (1 сенсор) против честного узла — узел остаётся `trusted`.
- Коллюзия двух сенсоров с normalized shared neighbors > threshold → кворум отклонён, оба получают strike.
- Immune plane flooding: приём более `immune_block_per_sensor_limit` блоков от одного сенсора за контакт — избыточные отбрасываются без проверки подписи.
- **Метрика immune overhead:** доля CPU/time, потребляемая immune plane per contact, < 10% от общего времени контакта.
- **Метрика quarantine slot utilization:** доля узлов в quarantine одновременно < `quarantine_max_scope` (10%). При превышении — глобальная пауза.

### Этап 19. Attack harness (вакцинация)

**Что строим:**

- Планировщик атак поверх trace-replay:
- `ReplayBot`: повтор старых beacon'ов/bundle'ов
- `FalseBeaconBot`: beacon с поддельным genome_id
- `SybilBot`: генерация N ложных идентичностей
- `BlackholeBot`: принимает bundle, не relay'ит
- `FlooderBot`: спам bundle'ами
- `FalseAlarmBot`: генерация ложных Threat'ов
- `ImmunePlaneFloodBot`: спам валидными Immune Block'ами для исчерпания CPU/memory
- `FitnessPoisonBot`: манипуляция трассой для завышения fitness
- `PoolCaptureBot`: наводнение пула ложными геномами
- Геном-кандидат прогоняется под каждой атакой.
- Fitness дополняется: `attack_resilience` (0..1) + штраф за ложные изоляции + diversity bonus.
- Кросс-валидация: отложенная трасс для финальной проверки.

**Критерий приёмки:**

- Геном с включённым immune-блоком показывает `attack_resilience ≥ 0.7` на всех 9 сценариях (8 + immune plane flooding).
- Head-to-head vs baseline (без immune): доставляемость под атакой выше на ≥15%.
- Откат на геном без immune-блока невозможен (constraints).
- **Метрика false-collusion rate:** процент ложных кворумов, сформированных коллюзией, которые не были отклонены топологической проверкой. Должен быть < 1%.

### Этап 20. Иммунная память

**Что строим:**

- Расширение GENOME-SPEC: блок `immune` с `known_threats` и constraints floor'ами.
- Запись удачных защитных стратегий в геном.
- Head-to-head: встреча с известным штаммом обрабатывается быстрее (меньше ложных срабатываний, быстрее переход в degraded), чем с новым.
- Constraints запрещают обнуление репутации сенсоров (защита от вырождения).
- **Invariants (не мутируются эволюцией вообще):**
  - `quorum_threshold ≥ 2`
  - `quarantine_max_scope ≤ 0.1`
  - `sensor_penalty_ttl ≥ 3600`
  - `sensor_epsilon ≥ 0.5` (differential privacy budget)
- **Constraints floor'ы (эволюция не может опустить ниже):**
  - `min_sensor_count ≥ 2`
  - `max_quorum_ttl ≤ 86400`

**Критерий приёмки:**

- Геном с `known_threats=["replay", "false_beacon"]` при повторной встрече с этими атаками реагирует в 2× меньше контактов (быстрее detection), чем наивный геном.
- Vironet не вырождается в параноика: false_positive_rate < 10% после 10 поколений эволюции под attack harness.
- Constraints не нарушаются ни в одном поколении. Invariants не мутируются.
- **Метрика revocation list size:** размер revocation-листа per узел < 10% от памяти, выделенной под immune plane. При превышении — LRU-эвикция.
- **Метрика bootstrap time:** время от первого контакта до достижения зрелости (maturation) < 48 часов в типичной DTN-среде (школьная/офисная трасса).
- **Метрика immune debt:** накопленный ущерб от ложных срабатываний за 1000 контактов < 5% от общего трафика (задержанные легитимные bundle'ы + время на appeals).

## 12. Mush Edge-кейсы: спам и иммунитет

**Принцип:** MyceRus не пропускает спам структурно. Если спам всё же появился — иммунитет распознаёт его по накоплению, а не по мгновенному срезу. Наказание — на основе verifiable evidence, не на основе мнения.

### 12.0. Почему спам структурно затруднён

| Барьер | Почему работает | Что ломает |
|--------|----------------|------------|
| **Адрес = согласие** | EID не публичен. Сообщение возможно только по адресу, полученному через QR/NFC + SNS-handshake. Нет глобального каталога, нет случайной рассылки. | Утечка адресной книги, компрометация контакта. |
| **Канал = грибница** | Групповой чат требует собственного Fruiting Gateway — выделенного узла-микросервера. Нет бесплатного broadcast'а. Владелец платит ресурсами. | Злоупотребление грибницей-хостом, массовая рассылка приглашений. |
| **Accept-bundle явный** | Добавление в контакты требует двухфазного SBP: Phase 1 (обмен pubkey) + Phase 2 (SNS-handshake + accept-bundle). Нельзя "подписать" контакт без физической встречи или явного согласия. | Accept-bundle flooding, contact list poisoning. |

Эти три барьера делают спам **осознанным и дорогим**, а не невозможным. Если спам прорывается через компрометацию или социальную инженерию — срабатывает иммунитет.

### 12.1. Формула: Структура → CUSUM → Иммунитет

```
Структурные барьеры (Адрес=согласие, Канал=грибница, Accept=явный)
        ↓
Если прорвался → CUSUM-сенсоры (накопление, не порог)
        ↓
Тихий режим (silent) → FSM эскалация → Quarantine
        ↓
Пользовательское решение (ручной блок)
```

### 12.2. Шесть векторов спама

| ID | Вектор | Как прорывается | Целевой компонент |
|----|--------|----------------|-------------------|
| **M1** | **Компрометация контакта** | Контакт Боба захвачен. Атакующий отправляет спам всем, кто знает Боба. | Контакт-лист жертвы |
| **M2** | **Accept-bundle flooding** | Атакующий отправляет accept-bundle'ы на десятки ключей из утечки. | SNS/SRE handshake |
| **M3** | **Channel invitation spam** | Владелец грибницы рассылает приглашения в канал массово. | Fruiting Gateway |
| **M4** | **Fruiting Gateway abuse** | Владелец грибницы рассылает сообщения участникам канала. | Fruiting Gateway relay |
| **M5** | **Relay poisoning** | Скомпрометированный relay-узел модифицирует bundle'ы при пересылке. | MGR forwarding |
| **M6** | **Contact list poisoning** | Атакующий "засеивает" контакт-лист жертвы ложными accept-bundle'ами. | Контакт-менеджер |

### 12.3. Шесть CUSUM-сенсоров

Все спам-сенсоры используют **CUSUM** (Cumulative Sum) — накопление отклонения от baseline, а не пороговый срез. Это критично в DTN, где нет real-time потока.

```rust
/// CUSUM-детектор: накапливает отклонение от baseline
/// Параметры (k, h) из Vironet-genома (могут мутировать под среду)
pub struct CUSUMSensor {
    baseline_rate: f64,              // медиана msg/контакт от этого ключа
    k: f64,                          // slack (минимальное отклонение для накопления)
    h: f64,                          // threshold (когда CUSUM срабатывает)
    cusum_pos: f64,                  // текущее положительное накопление
    cusum_neg: f64,                  // текущее отрицательное накопление
}

impl CUSUMSensor {
    pub fn observe(&mut self, observed: f64) -> Option<Alarm> {
        let deviation = observed - self.baseline_rate;
        self.cusum_pos = (self.cusum_pos + deviation - self.k).max(0.0);
        self.cusum_neg = (self.cusum_neg - deviation - self.k).max(0.0);
        
        if self.cusum_pos > self.h {
            Some(Alarm::HighActivity { score: self.cusum_pos })
        } else if self.cusum_neg > self.h {
            Some(Alarm::LowActivity { score: self.cusum_neg })
        } else {
            None
        }
    }
}
```

| ID | Сенсор | CUSUM-параметр | Что измеряет |
|----|--------|---------------|--------------|
| **S1** | **ContactRateSensor** | `observed = msg_per_contact` | Частота сообщений от одного контакта. Baseline пересчитывается при каждом контакте. |
| **S2** | **ContentDiversitySensor** | `observed = duplicate_ratio` | Дубликаты сообщений. Copy-paste накапливает отклонение быстрее уникальных. |
| **S3** | **AcceptRequestSensor** | `observed = accepts_per_window` | Частота accept-bundle'ов. Аномалия: ключ принимает больше контактов, чем исторически. |
| **S4** | **InvitationRateSensor** | `observed = invites_per_window` | Применяется к Fruiting Gateway (кто рассылает приглашения). |
| **S5** | **RecipientDiversitySensor** | `observed = unique_recipients_per_window` | Число уникальных получателей. **Требует gossip-аттестаций** (медленно, но единственный способ получить полную картину). |
| **S6** | **GribnitsaReputationSensor** | `observed = complaint_ratio` | Репутация грибницы-хоста. Участники голосуют "доверие/недоверие". |

**Почему CUSUM:**
- В DTN bundle уже в пути — real-time блокировка невозможна.
- CUSUM реагирует на **накопленное отклонение**, а не на мгновенный скачок.
- Параметры (k, h) могут быть эволюционными (Vironet мутирует их под среду).
- Одиночные всплески (ЧС, оповещение) не срабатывают — нужно **накопление**.

**Защита от boiling frog (медленного дрейфа baseline):**

```rust
pub struct DualCUSUMSensor {
    fast: CUSUMSensor,           // окно ~20 наблюдений, ловит резкий спам
    slow: CUSUMSensor,           // окно ~200 наблюдений, ловит дрейф
    baseline: MedianBaseline,    // скользящая медиана с ограничением скорости
}

pub struct MedianBaseline {
    history: VecDeque<f64>,      // история наблюдений
    max_window: usize,           // макс размер (например, 500)
    max_update_rate: f64,        // макс изменение baseline за контакт (например, 5%)
}

impl MedianBaseline {
    pub fn update(&mut self, observed: f64) {
        self.history.push_back(observed);
        if self.history.len() > self.max_window {
            self.history.pop_front();
        }
        
        let new_median = median(&self.history);
        let old_median = self.current;
        let delta = (new_median - old_median).abs() / old_median;
        
        if delta > self.max_update_rate {
            // Ограничиваем скорость обновления baseline
            self.current = old_median * (1.0 + self.max_update_rate.signum() * self.max_update_rate);
        } else {
            self.current = new_median;
        }
    }
}
```

**Два масштаба:**
- **Fast-CUSUM:** окно ~20 наблюдений, чувствителен к резким всплескам (спам-атака).
- **Slow-CUSUM:** окно ~200 наблюдений, чувствителен к медленному дрейфу (boiling frog).
- Тревога от **любого** из них.

**Медианный baseline:**
- Медиана устойчива к выбросам лучше среднего/EWMA.
- Ограничение скорости обновления (`max_update_rate = 5%`) предотвращает следование baseline за дрейфом атакующего.

```rust
                },
            }]
        } else {
            vec![]
        }
    }
    
    fn on_contact(&mut self, _event: &ContactEvent) -> Vec<SensorEvent> {
        self.contact_count += 1;
        if self.contact_count % self.rotation_period == 0 {
            self.rotate_decoys();
        }
        vec![]
    }
    
    fn rotate_decoys(&mut self) {
        // Генерируем новые decoy EID, старые архивируем на decoy_grace_period контактов
        let new_decoys = generate_decoy_eids(3);
        self.decoy_eids = new_decoys;
    }
}
```

**Почему это сильно:**
- **Нулевой false positive по построению.** Bundle на decoy EID не может прийти легально — этот адрес никому не выдавался.
- **Детектирует A1, A4, A5.** Replay beacon'а, spoofing, scanning — всё это приведёт к попытке отправки на decoy.
- **Обучающий сигнал для Vironet.** Атакующие сами выдают свои паттерны — DecoyEidSensor собирает «вакцину».
- **Дёшево.** Один фиктивный EID в beacon'е — нулевые накладные расходы.

**Ограничение:** decoy EID не должен быть «слишком привлекательным» (например, short EID), иначе атакующий может угадать. Генерация: `decoy = hash(random_nonce || node_pubkey || epoch)`.

### 12.4. Разделение evidence: Verifiable vs Reputational

| Тип | Что это | Пример | Как используется |
|-----|---------|--------|----------------|
| **Verifiable** | Объективные факты, верифицируемые любым узлом | Частота, дубликаты, accept-flooding | Формирует `Threat`-bundle с `evidence_hash`. **Quarantine только на verifiable evidence.** |
| **Reputational** | Субъективное мнение пользователя | "Это спам" (кнопка "пожаловаться") | Не вызывает quarantine. Накапливает strike в таблице репутации. При ≥N strike'ов — сенсор теряет вес. |

**Принцип:** Quarantine — тяжёлое решение. Оно требует **verifiable evidence**. "Мне не нравится" — reputational evidence, оно не может изолировать узел.

### 12.5. DTN-специфика спам-детекции

| DTN-ограничение | Как адаптируем |
|-----------------|----------------|
| **Нет real-time** | Bundle уже в пути. Блокировка retroactive — следующие bundle'ы уже отфильтрованы. |
| **Локальная защита** | Сенсор на одном узле не знает о сенсоре на другом. Каждый узел принимает независимое решение. Глобальный вердикт — необязательная роскошь. |
| **Gossip-аттестации** | RecipientDiversitySensor требует: получатели сравнивают, от кого они получали спам. Это gossip между контактами. **Медленно**, **ненадёжно**, но **единственный способ** получить полную картину. |

### 12.6. FSM с тихим режимом (Silent Mode)

Традиционный FSM: `trusted → watch → degraded → quarantined`. В DTN это слишком резко.

**Расширенный FSM для спам-контактов:**

```
trusted ──► watch ──► silent ──► degraded ──► quarantined
              │          │           │
              └──────────┴───────────┘
                 (ручной сброс пользователем)
```

| Состояние | Что происходит | Что видит пользователь |
|-----------|---------------|----------------------|
| **watch** | Логирование, без ограничений. | Ничего. |
| **silent** | Bundle'ы **принимаются**, но **не показываются**. Лежат в теневом inbox. | 🟡 "Необычная активность". Можно заглянуть в теневой inbox. |
| **degraded** | Relay-приоритет снижен. Сообщения доходят, но медленнее. | 🔴 "Контакт ограничен". |
| **quarantined** | Полный отказ в relay. Уже принятые bundle'ы остаются. | "Временно заблокирован сетью". |

**Эскалация:**
- CUSUM срабатывает → `watch`.
- CUSUM продолжает накапливать → `silent`.
- Кворум сенсоров → `degraded`.
- Повторный кворум + bridge-guard → `quarantined`.

**Апелляция:**
- Пользователь вручную переводит из `silent` в `trusted` → CUSUM сбрасывается на этом узле.
- Другие узлы не знают об апелляции — их CUSUM не сбрасывается.

### 12.7. Пользовательский UX

| Сценарий | Что видит пользователь |
|----------|----------------------|
| Контакт в `silent` | Индикатор 🟡. Теневой inbox. Можно восстановить. |
| Кнопка "пожаловаться" | Генерирует **reputational evidence**. Не quarantine. Увеличивает strike count. |
| Лог иммунной активности | `[14:32] ContactRateSensor: Боб — CUSUM превышен (score: 3.2)`<br>`[14:35] Контакт переведён в silent mode`<br>`[14:40] Пользователь восстановил контакт, CUSUM сброшен` |

### 12.8. Контрмеры

| Контрмера | Когда | Как |
|-----------|-------|-----|
| **Accept-bundle throttle** | AcceptRequestSensor срабатывает | Лимит на accept'ы от одного ключа (например, 1/час). |
| **Channel mute** | InvitationRateSensor срабатывает | "Заглушить" канал (не уведомления, но остаёмся участником). |
| **Rate limiting** | ContactRateSensor срабатывает | Снижение приоритета bundle'ов спамера в очереди relay. |

### 12.9. Сценарии валидации

```
Сценарий J. ContactRateSensor + CUSUM (M1)

Участники: 10 узлов, каждый знает 3 контакта.
Атака: Узел 5 (Боб) захвачен. Отправляет 50 сообщений за 10 контактов
       (норма Боба: 2 msg за 10 контактов).
Ожидаемое: ContactRateSensor CUSUM накапливает отклонение.
           После 10-го сообщения CUSUM > h → переход в watch.
           После 30-го сообщения → silent (теневой inbox).
Метрика: detection time ≈ 10 сообщений;
         ложные срабатывания на легитимной массовой рассылке (ЧС) = 0
         (ЧС — единичное событие, CUSUM не накопит).
```

```
Сценарий K. Accept-bundle flooding (M2)

Участники: 20 узлов.
Атака: Узел 3 отправляет accept-bundle'ы на 15 ключей за 5 контактов.
Ожидаемое: AcceptRequestSensor CUSUM срабатывает.
           Accept-bundle throttle: лишние accept'ы отбрасываются.
           Узел 3 переходит в watch.
Метрика: >80% ложных accept'ов отброшены;
         легитимные accept'ы (встреча с новым контактом) не затронуты.
```

```
Сценарий L. Gossip-аттестации + RecipientDiversitySensor (M5)

Участники: 8 узлов, сеть clique (все знают всех).
Атака: Узел 4 отправляет сообщения всем 7 контактам.
Ожидаемое: RecipientDiversitySensor на каждом получателе фиксирует получение от узла 4.
           Gossip-аттестации: узлы сравнивают, от кого получали.
           Кворум (3+ узла подтверждают) → Threat против узла 4.
Метрика: gossip достигает консенсуса за < 5 контактов;
         ложные срабатывания при нормальной групповой переписке = 0.
```

## 14. Partition reconciliation (восстановление после разделения)

В DTN сеть естественно разделяется на партиции (нет связи между регионами). Когда связь восстанавливается, узлы из разных партиций могут иметь конфликтующие состояния FSM, revocation-листы и репутации.

### 14.1. Проблема

- Партиция A поместила ключ K в `quarantined`.
- Партиция B не получила Threat-bundle и считает K `trusted`.
- При восстановлении связи — конфликт состояний.

### 14.2. Принцип: union-with-expiry + last-writer

| Сценарий | Правило |
|----------|---------|
| **Одинаковые состояния** | Ничего не делаем. |
| **Разные состояния, оба non-quarantine** | Берём более строгое (`quarantined` > `degraded` > `watch` > `trusted`). |
| **Quarantine vs trusted** | Если quarantine имеет валидный verifiable evidence и TTL не истёк — quarantine wins. Если TTL истёк — trusted wins. |
| **Конфликтующие revocations** | `last-writer-wins` по timestamp (больший monotonic counter). Revocation с более свежим timestamp перезаписывает старый. |
| **Репутация сенсоров** | Мержим таблицы: (подтверждённые тревоги, ложные тревоги) = сумма из обеих партиций. Если конфликт — last-writer по timestamp. |

### 14.3. Hash-chain immune log

Каждый узел ведёт хэш-цепочку иммунных событий:

```rust
pub struct ImmuneLogEntry {
    pub event: ImmuneEvent,           // quarantine, watch, revoke, appeal
    pub target: Ed25519PublicKey,
    pub timestamp: Timestamp,
    pub evidence_hash: Hash,
    pub prev_hash: Hash,              // hash(prev_entry)
}

pub struct ImmuneLog {
    pub entries: Vec<ImmuneLogEntry>,
    pub head: Hash,                   // hash(last_entry)
}
```

**Reconciliation через hash-chain:**
1. При контакте узлы обмениваются `head` своих цепочек.
2. Если `head` совпадают — ничего не делаем.
3. Если `head` различаются — ищем точку расхождения (бинарный поиск по истории).
4. Синхронизируем только **дельту** (записи после точки расхождения).
5. Каждая запись верифицируется по подписи эмитента.

**Burden of proof:** чужой quarantine не применяется напрямую:
- Чужой `quarantined` → применяется как `silent` или `degraded` (не `quarantined`).
- Полный `quarantined` — только после подтверждения **локальным сенсором** или **локальным кворумом**.
- Это предотвращает наследование чужой ошибки (ложная тревога, коллюзия).

### 14.4. Алгоритм reconcile

```rust
pub fn reconcile_partition(
    local_fsm: &FSMTable,
    remote_fsm: &FSMTable,
    local_log: &ImmuneLog,
    remote_log: &ImmuneLog,
) -> ReconciliationResult {
    // 1. Hash-chain sync: найти точку расхождения, синхронизировать дельту
    let delta = sync_delta(local_log, remote_log);
    
    // 2. FSM: union-with-expiry + burden of proof
    let merged_fsm = merge_fsm(local_fsm, remote_fsm, |local, remote| {
        if local.state == remote.state { return local; }
        
        // Чужой quarantine → только silent/degraded
        let effective_remote = if remote.is_foreign {
            match remote.state {
                FSMState::Quarantined => FSMState::Degraded,
                FSMState::Degraded => FSMState::Silent,
                _ => remote.state,
            }
        } else { remote.state };
        
        match (local.state, effective_remote) {
            (FSMState::Quarantined, _) if local.ttl_remaining() > 0 => local,
            (_, FSMState::Quarantined) if effective_remote.ttl_remaining() > 0 => effective_remote,
            _ => stricter_state(local.state, effective_remote),
        }
    });
    
    ReconciliationResult { fsm: merged_fsm, delta }
}
```

### 14.5. Граница

- Reconciliation происходит **только при контакте** — нет фоновой синхронизации.
- Если партиции никогда не встретятся — их состояния остаются расходящимися. Это нормально для DTN.
- Размер reconciliation-bundle ограничен: передаются только delta (изменения с момента последнего контакта).

## 15. Bootstrap-режим (genesis-якоря)

Новый узел, присоединяющийся к сети, не имеет истории, репутации сенсоров или baseline'ов. Он уязвим к любым атакам, пока не «выстреляет».

### 15.1. Проблема

- Новый узел не знает, кому доверять.
- Любой первый контакт может быть атакующим.
- Без истории сенсоры не могут вычислить baseline.

### 15.2. Genesis-якоря

```rust
pub struct GenesisAnchor {
    pub pubkey: Ed25519PublicKey,     // ключ доверенного узла
    pub signature: Signature,         // подпись creator'а или администратора
    pub ttl: Duration,                // срок действия якоря
    pub max_trust_level: FSMState,    // максимальный уровень доверия через якорь (например, watch)
}
```

**Как работает:**
- Новый узел загружает 1–3 genesis-якоря из-of-band (QR-код, NFC, предустановка).
- При первом контакте с узлом, чей pubkey совпадает с якорем — установка `watch` (не `trusted`).
- Якорь даёт **начальное направление**, не абсолютное доверие.
- После `ttl` якорь истекает — узел полагается только на накопленную историю.

### 15.3. Cap на действия нового узла

| Действие | Ограничение | Почему |
|----------|-------------|--------|
| **Relay** | Может relay только bundle'ов от якорных узлов | Предотвращает spread атаки через новый узел |
| **SNS-handshake** | Может инициировать, но не принимать от незнакомых | Предотвращает accept-bundle poisoning |
| **Sensor** | Не может быть сенсором первые N контактов | Предотвращает Sybil-сенсор |
| **Vironet voting** | Не может голосовать первые M эпох | Предотвращает pool capture через новые узлы |
| **Quarantine** | Не может инициировать quarantine | Защита от ложных тревог новичка |

### 15.4. Вызревание (maturation)

```rust
pub struct MaturationTracker {
    pub contacts_observed: usize,     // число наблюдаемых контактов
    pub contacts_initiated: usize,    // число инициированных контактов
    pub bundles_relayed: usize,       // число relayed bundle'ов
    pub maturation_threshold: usize,  // порог полной зрелости (например, 50 контактов)
}

impl MaturationTracker {
    pub fn is_mature(&self) -> bool {
        self.contacts_observed >= self.maturation_threshold
    }
    
    pub fn can_act_as_sensor(&self) -> bool {
        self.contacts_observed >= self.maturation_threshold / 2
    }
}
```

### 15.5. Граница

- Bootstrap-режим — это **training wheels**, не пожизненная инвалидность.
- Узел выходит из bootstrap по достижении зрелости, а не по времени.
- Без genesis-якорей узел может присоединиться, но будет крайне ограничен (только passive relay, нет инициации контактов).

## 16. Appeals (апелляции)

Если узел считает, что quarantine несправедлив, он может подать апелляцию. Это не отменяет quarantine автоматически, но запускает процесс пересмотра.

### 16.1. Формат апелляции

```rust
pub struct AppealBundle {
    pub target_key: Ed25519PublicKey,   // кого quarantine'или (обычно self)
    pub quarantine_evidence_hash: Hash, // хэш evidence, на основе которого quarantine
    pub counter_evidence: Vec<VerifiableEvidence>, // доказательства невиновности
    pub timestamp: Timestamp,
    pub ttl: Duration,
    pub signature: Signature,
}
```

### 16.2. Типы counter-evidence

| Тип | Когда применяется | Пример |
|-----|------------------|--------|
| **Alibi** | Узел был офлайн во время атаки | Timestamp'ы контактов показывают, что узел не мог отправлять bundle'ы в окно атаки |
| **Key rotation** | Ключ был скомпрометирован, но уже ротирован | Новый ключ + revocaton старого + доказательство владения новым ключом |
| **Behavioral baseline** | Поведение было нормальным в контексте | Доказательство, что "аномальная" активность была легитимной (например, оповещение о ЧС) |
| **Bridge-hostage** | Узел — мост, quarantine разрушит связность | Топологическое доказательство, что узел единственный путь между сегментами |

### 16.3. Процесс апелляции

```
Узел подаёт AppealBundle → распространяется через mesh
        ↓
Соседи, получившие Appeal, проверяют counter-evidence
        ↓
Если counter-evidence верифицируется → кворум сенсоров голосует
        ↓
Кворум подтверждает апелляцию → Revoke-бандл против quarantine
        ↓
Узел переходит из quarantined → probation (усиленный мониторинг)
```

### 16.4. Ограничения

- **Не отменяет quarantine мгновенно.** Даже успешная апелляция даёт `probation`, не `trusted`.
- **TTL апелляции.** Если апелляция не рассмотрена за `appeal_ttl` — она истекает.
- **Одна апелляция на quarantine.** Повторные апелляции от того же ключа по тому же incident'у игнорируются.
- **Cost.** Апелляция требует relay-ресурсов — спам апелляциями экономически невыгоден.

### 16.5. Граница

- Апелляция — это не "отмена наказания", это "пересмотр на основе новых данных".
- Сеть не обязана рассматривать апелляцию. Узел может остаться в quarantine до истечения TTL.
- Успешная апелляция не восстанавливает репутацию сенсоров, которые подняли ложную тревогу — они всё ещё получают strike.
